How we work

The FringeIsland development system — four axes, five diagrams, eighteen flagged gaps. Click any gap card to expand its commentary.

Overview

How this document is organised · what the four axes are · how to navigate

This document describes how FringeIsland is actually developed — end-to-end, from ecosystem purpose down to shipped code. It has two purposes: a self-orientation aid for the sole developer, and onboarding material for future contributors.

The development system has four axes. Each lives on its own tab with a diagram and prose. You can read them in any order, but the order below is the one that builds understanding fastest.

The four axes

  • Decomposition cascade (tab 1) — the vertical axis. Vision → Entities → Capabilities → Features → Tasks.
  • Cadence and waves (tab 2) — the horizontal axis. How time is structured: cycles, cooldowns, the six waves, retros.
  • Execution (tabs 3 and 4) — the work-level axis. Part 1: how items get refined and onto the board. Part 2: the per-task build loop.
  • Agent routing (tab 5) — the entry axis. How an agent or human enters the system and builds context progressively.

On gaps

The system has known documentation and design gaps. They are flagged inline in each chapter and consolidated on the Gaps tab. They are surfaced honestly because the primary reader (Stefan) is using this document to spot what's missing. Future contributors should treat the gap list as a to-do, not a stable description of the system.

As of 2026-04-19 there are eighteen flagged gaps. None block current solo-operator work. All compound as the system scales toward the 50-plus-contributor target.

1 — Decomposition cascade

The vertical axis · from ecosystem vision down to the tasks that ship

Work descends through five levels: Vision → Entities → Capabilities → Features → Tasks. Five verticals thread through every level as cross-cutting obligations, not a sixth level. The same FEAT-*.md file carries a feature from maturity 0 through 6.

The verticals thread the whole cascade because they derive their authority from vision-level principles (e.g. Privacy over commercial opportunity). Every feature spec addresses all five — no blanks.

Gaps on this axis

  • G-01 · Whisp architectural placement (L2)Medium

    Vision names Whisp as a core structural concept, operating across all three worlds as companion voice, perceptual richness, and active instrument. At L2 none of the current entities owns Whisp. Natural candidates: Intelligence (DS-7), World Model (DS-1), or a cross-service abstraction.

    Every Whisp-involving feature has no routing to an owner — it falls into OPEN_QUESTIONS.md by default.

    Proposed fix: ADR that assigns Whisp to an existing domain service, creates a new one, or locks "Whisp is cross-cutting; its features are paired specs between Intelligence and World Model."

  • G-02 · Cross-product feature sync (L4)Medium

    The ecosystem-decomposition skill defines the paired-spec pattern (Hub UI + Platform data model, linked via "Platform dependencies"). The linking is named; the synchronization is not. When FEAT-H005 changes its acceptance criteria, nothing alerts FEAT-PD003's owner.

    The DoR check fires once at spec creation; nothing fires afterwards.

    Proposed fix: extend ecosystem-decomposition skill with a "cross-product sync" procedure, ideally invoked during doc-health-check at cycle boundaries.

  • G-03 · Vertical specs are scaffolds (cross-cut)High

    The highest-priority gap in the whole document.

    Five vertical spec files exist. Their §1 (Purpose) and §2 (Scope) are written. Their §3 (tier-specific obligations), §4 (cross-cutting checklists that feed DoD), §5 (tooling), and §6 (failure modes) are all marked "currently partial — to be refined."

    Meanwhile, every feature spec is forced to complete a Vertical Impact section against those stubs. Authors necessarily invent implicit definitions. Those definitions diverge across specs. When the vertical specs are eventually populated, a subset of shipped features will be out of compliance with the newly-explicit rules.

    Proposed fix: populate §3 through §6 of each of the five vertical specs. Probably a full cycle's work. Suggested order: Privacy → Observability → Administration → Notifications → Transactions.

2 — Cadence and waves

The horizontal axis · how time is structured

Three bands operating at different frequencies. Waves are thematic focus buckets that overlap in time — not sequential gates. Cycles are the operational rhythm: 3-week build + 1-week cooldown. Retros nest at four scales — daily, weekly, cycle, wave — reusing one template.

Items from any wave can coexist in a single cycle. What enforces concurrency is the WIP limit (3 items at the review stage), not wave boundaries.

Gaps on this axis

  • G-04 · Wave ↔ roadmap relationshipMedium

    PROCESS.md §3 references ecosystem, product, and platform roadmaps alongside the wave model. If ECOSYSTEM_ROADMAP.md shows "NOW: Ferd / NEXT: Eid / LATER: Hamn" it duplicates the waves band. If it shows NOW/NEXT/LATER features independent of wave grouping, it's a separate planning layer.

    Proposed fix: session decision during cooldown. Three options: (a) waves replace roadmaps, (b) roadmaps are NOW/NEXT/LATER within waves, (c) they are orthogonal.

  • G-05 · Review queue not operationalizedHigh

    Tasks have status: review and assigned_to in frontmatter. No document describes how a reviewer is chosen, how a task flows from in_progress to review to approved, or how the WIP-at-review rule actually bites. The bottleneck has no enforcement mechanism.

    Proposed fix: extend feature-development skill with a Review section covering reviewer assignment, review checklist, review outcomes, and WIP enforcement.

  • G-06 · Multi-agent task lockingHigh

    WIP is a personal-kanban construct. At the 50+ parallel contributors target, two agents can independently pick up the same TASK-*.md. The assigned_to field is the obvious lock primitive; no atomicity rule or collision detection is specified.

    Proposed fix: ADR on multi-agent task acquisition. Probably (a) assigned_to empty-or-self-only rule, (b) explicit claim step in feature-development skill, (c) optional TASK-LOCK primitive for high-contention cases.

  • G-07 · Ferd DoD emptyMedium

    Wave-spec template has the DoD shape. docs/planning/waves/ferd.md has not had Ferd-specific criteria populated. "Are we done with Ferd?" cannot be answered concretely.

    Proposed fix: populate the DoD section using the wave-planning skill. Timing: during the cooldown before Eid ramps up.

  • G-08 · PROCESS.md §3 WIP driftLow

    Research intent: WIP at review stage. PROCESS.md §3 current text: "WIP limit: 3 items in doing at any time." One-word fix.

    Proposed fix: edit PROCESS.md §3: "in doing" → "in review". CHANGELOG entry.

3 — Execution: backlog refinement and the kanban board

Part 1 of the execution axis · where work lives before and during a cycle

Two stages stacked: progressive elaboration (maturity 0→4 as same-file evolution) feeds the six-column kanban board. On the board, the same feature spec continues advancing — 5-in-cycle when pulled into a cycle, 6-done when all its tasks pass DoD.

The full pipeline: 0→6 on one file

Refinement (0→4) — product owner's lane. The diagram's top row. Research before specification; DoR is the gate into the board.

On-board (5→6) — developer's lane. The diagram's bottom row.

  • 5 In cycle — the YAML flag on FEAT-*.md flips from 4-ready to 5-in-cycle when a cycle pulls the item. TASK-*.md files are generated. Maturity 5 spans the Doing and Review columns — a task can be in Review while its parent feature is still at 5-in-cycle.
  • 6 Done — when every task on the feature passes DoD, the developer flips the YAML to 6-done and fills in the Implementation notes section (what was built, where, key files, RPCs, decisions). The spec has reshaped itself from proposal into record. Task files are deleted after the cycle retrospective commits.
Maturity and kanban columns are orthogonal. Maturity is a flag on the feature spec (one per feature). Kanban columns are status: on task files (many per feature). A feature reaches 5-in-cycle when any of its tasks enters Doing; it reaches 6-done only when all its tasks are Done and Implementation notes are written.

Gaps on this axis

  • G-09 · Refinement ritual undocumentedMedium

    Maturity levels are named; how items actually get refined 0→4 in practice is not. Is it a recurring meeting, a solo shaping session, a back-and-forth with Claude?

    Proposed fix: extend ecosystem-decomposition skill with a refinement section. Likely: 0→1 is solo articulation; 1→2 is research (spike or research doc); 2→3 is story writing with Given/When/Then; 3→4 is DoR pass.

  • G-10 · Board mechanic unchosenMedium

    Six columns depicted; no document says where the board physically lives. GitHub Projects? Linear? A markdown table? A query over YAML frontmatter?

    Proposed fix: session decision. Separate two timeframes — current-state tool (markdown table + grep over YAML is probably enough) and scale tool (flag for Eid or later wave-boundary decision).

  • G-14 · Discovery 0→2 flow orphanedMedium

    The ecosystem-decomposition skill covers levels 1-5 as artifacts. The 0→1 transition (raw idea to concept) and 1→2 transition (concept to explored) have no explicit home.

    Proposed fix: add a level-0 section to the ecosystem-decomposition skill covering capture, articulation, and exploration.

  • G-18 · Research pathway under-specifiedMedium

    Three research mechanisms exist but aren't unified: (1) maturity-2 as a research stage on a feature spec; (2) type:spike as a work-item type with its own template; (3) docs/research/ holding long-form research reports.

    Missing: when does a question warrant a spike vs a research report? How do spike findings flow back into affected feature specs? How do research-report conclusions become ADRs, skill updates, or new features?

    Proposed fix: add a Research pathway section to ecosystem-decomposition skill or PROCESS.md §6 distinguishing spike (cycle-scoped) from research report (wave- or cross-wave-scoped), and describing how findings feed back to affected specs.

4 — Execution: the per-task build loop

Part 2 of the execution axis · what happens when a task moves into Doing

Research → Plan → Annotate → Implement is the canonical working pattern with an AI coding agent. Markdown files serve as shared mutable state between Stefan and the agent. One Given/When/Then scenario in the feature spec feeds three test layers. The Testing Trophy shape has integration tests as the biggest band.

"Don't implement yet" is the guard phrase that prevents the agent from jumping to code before the plan is approved.

Gaps on this axis

  • G-11 · TDD overstated vs risk-basedLow

    Root CLAUDE.md mandates TDD. The research report permits risk-based testing as an alternative. The stricter version was inherited without an explicit decision.

    Proposed fix: either (a) drop the strict TDD mandate to match the research, or (b) keep it and justify the stricter position in an ADR. Low priority — the tension is small in practice.

  • G-12 · Given/When/Then to test translationHigh

    The feature-spec template requires Given/When/Then scenarios. Jest, Playwright, and pgTAP exist in the stack. No document describes how a scenario in a feature spec becomes a concrete test case.

    The single highest-leverage practice from the research — one artifact serving as spec, tests, and AI prompt — has no documented translation mechanic.

    Proposed fix: extend feature-development skill with a "scenarios to tests" section. A worked example showing the same scenario landing in a unit test, integration test, and E2E test.

  • G-13 · Build hygiene unspecifiedMedium

    No branching strategy. No commit cadence beyond "conventional commits". No PR shape. No guidance on when to open, how to structure, who reviews. At 50+ contributors the absence is load-bearing.

    Proposed fix: extend feature-development skill with a Build Hygiene section covering branching, commit cadence, PR shape. Likely needs an ADR for the branching strategy.

5 — Agent routing

The routing axis · how an agent enters the system and builds context

Eight steps of progressive context loading: root CLAUDE.md → AGENTS.md → PROCESS.md → matched skill → tier CLAUDE.md → owner README → feature spec → task file. At step 4, pick one of the four skills (ecosystem-decomposition, feature-development, wave-planning, doc-health-check). Never load everything at once.

Tell: new contributors should be able to start useful work within 30 minutes of opening the repo. The eight-step path is tuned to make that possible.

Gaps on this axis

  • G-15 · Cross-tier entry orderMedium

    Step 5 says "the tier CLAUDE.md for where the work lives." For cross-tier features (Hub UI + Platform data model), which tier loads first is undefined. Wrong order means less-relevant constraints get internalized first.

    Proposed fix: rule in root CLAUDE.md or feature-development skill — e.g. "For cross-tier tasks, load the consumer tier first, then the provider tier."

  • G-16 · Skill chaining undocumentedMedium

    Most real work crosses skills. ecosystem-decomposition to write a spec, then feature-development to build it. feature-development to mark 6-done, then doc-health-check to verify. The chains are currently tacit.

    Proposed fix: add a "common chains" section to PROCESS.md §6.5 or to root CLAUDE.md. Name the three or four chains that matter most.

  • G-17 · AGENTS.md precedence across toolsLow

    Three AGENTS.md files exist: /AGENTS.md (canonical for Claude), configs/codex/AGENTS.md, configs/opencode/AGENTS.md. No precedence rule.

    Proposed fix: ADR declaring /AGENTS.md canonical; tool-specific copies must not contradict. Add a doc-health-check comparison at cycle boundary.

The pattern visible across the register

Strong bookends (vision at the top; DoD at the bottom), weak middle (how items move through maturity, how specs translate to tests, how the build loop is documented, how review actually handshakes). Seven of the seventeen gaps are middle-layer gaps. This is not accidental — it reflects an ecosystem that has invested heavily in strategic scaffolding and lightly in tactical scaffolding.

The highest-leverage single move is probably expanding the feature-development skill to cover the build loop, the Given/When/Then to test translation, and build hygiene. Three gaps closed by one skill expansion.
