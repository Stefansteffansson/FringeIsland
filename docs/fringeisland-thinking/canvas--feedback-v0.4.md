# Phase 1 feedback (input to spec v0.5)

Collected from Stefan's first use, 2026-09-12 onward.

1. Empty landing gives no guidance. With 0 tabs the landing should show a "Start here" card: Import the discovery log (statements preset), then New tab, then drag from Unplaced. Hide it once the first tab exists.
2. Import dialog: file list truncates repo paths so the distinctive end is cut. Show file name first, folder path as a muted second line, full path in a tooltip; add a draggable divider between the source column and the preview pane; make the "suggested" labels part of the row, not a separate faint column.
3. Overlays over the landing image are unreadable: the glass surface at 0.55 alpha is designed for the blurred, dimmed canvas backdrop, not the full-contrast landing. Rule: any modal (import, dialogs, reader overlay) dims the whole backdrop to ~0.65 black and uses the glass2 surface (0.75) or higher; body text in dialogs at full text token, never muted; the split-rule explanation must be readable.
4. Import preview: ticking. Add "select all / none", show "N to write, M already present, K unticked" above the Write button, and make it visible that unticked entries can be brought in later by re-importing the same file (re-import writes only missing ones, per 5.7). Verify the built re-import actually skips existing entity files rather than duplicating or refusing.
5. Typography: Instrument Serif looks squashed below ~40px (empty-tab heading, inspector title, overlay title). Rule: Instrument Serif only for the landing title; all other headings Manrope 600 (inspector title 16px/600, empty-state heading 18px/600, overlay title 20px/600). Update section 17 and tokens.
6. Light theme: canvas backdrop too bright and saturated; glass panels lose contrast against it. Backdrop image in light mode at brightness ~1.15 and saturation ~0.5 with a stronger overlay (light ground at 0.7 alpha); panels use glass2 (0.75) in light mode.
7. Import tick boxes: verify unticked entries are actually excluded (Stefan unticked some on first import; re-import found nothing missing). Session-note cards (4) are expected alongside the 48 statements; the preset description should state that count up front.
8. Reader overlay is too transparent; cards behind bleed through the text. Overlay surface at 0.94 alpha (glass feel only at the edges), backdrop dimmed to ~0.6, text column always on an opaque ground. Same rule for every modal (item 3).
9. Importer, statements preset: the "Held" block is captured into the held: field AND left in the body, so the overlay shows it twice. Strip captured blocks (held, refines) from the body; the overlay shows held once, as the boxed block above the statement. Re-running the import on already-written files should offer "update bodies" (5.7) so the existing 48 can be cleaned in place.

10. Edge delete uses the browser's native confirm() ("Delete this edge from the global edge list?"). Rule: never native alert/confirm/prompt; every dialog is an in-app glass dialog (item 3 styling). Wording in user terms, not storage terms. Decided (Stefan, 2026-09-12): Option 1. Delete removes the edge immediately, no confirmation; Ctrl Z restores it. Same rule for deleting placements, native cards and frames; only entity-file deletion (Phase 4) and tab deletion with children keep an in-app dialog.

11. Deleting a frame (Delete key, inspector "Delete frame", toolbar trash) removes the cards inside it too. Rule: deleting a frame removes only the frame; its cards stay on the tab at their positions. "Ungroup" and "Delete frame" therefore differ only in that Ungroup keeps the frame's title nowhere; both leave cards intact. Removing cards from the tab is a separate action (select cards, Delete = unplace; entity files are never deleted from the canvas). Frame delete is undoable, no confirm (item 10). Observed: undo needed two Ctrl Z (first the frame, then the cards) -> the delete was journaled as two actions. Rule: one user action = one undo step (compound actions are grouped in the undo stack and the journal).

12. Dark mode not found by Stefan: the moon icon in the top bar is not discoverable. Tooltip "Theme: light / dark / system", the icon reflects the current state, choice persisted in config.json (ui.theme) and applied before first paint (no flash). Also a Theme row in Settings. (Verify the toggle actually switches the canvas, not only the icon.)

13. Edge labels: the type label sits on the line with a bordered pill, and the line shows through the text. Rule: label rendered above the edge (EdgeLabelRenderer / higher z-index than the path), no border, no pill, no background fill at all: the path itself is interrupted for the label's width plus 6px on each side (a gap in the stroke, e.g. a mask or the path split into two segments around the label's midpoint), so the canvas shows through the gap and only the text sits there; text 11px Manrope 600 in the edge type color. Selected edge: label text brightens, still no border. Same treatment for the note if shown.

14. Reader overlay opens read-only; per 10.6 it must open directly in edit mode for every kind (native notes, editable entities, locked statements). The body is an editor from the first frame; the formatting bar is visible; nothing is written unless content changed. Locked statements: the editor is live, and closing with changes triggers the revision flow (reason, minor) instead of a plain save. In Phase 1 (no write-back yet) the editor still opens in edit mode, but closing with changes shows "Revisions arrive in Phase 4; changes discarded" and the Revise button stays disabled. Phase 4 turns it on; no read-only mode exists at all. Items 8 and 9 confirmed in dark theme with this overlay.

15. New note from the toolbar button appears under the toolbar (placed at the click position). Rule: toolbar-created cards (Note, Entity pick, Frame, Media) are placed at the center of the visible viewport, then nudged by the no-overlap rule to the nearest free spot; only the hotkey path (N, E, ...) uses the cursor position, and never inside the toolbar/pill/panel areas. A new note opens straight into inline edit with the title selected.

16. Delete key on a selected native note does nothing (or asks). Rule: Delete / Backspace on any selection acts immediately, no confirm, undoable with Ctrl Z: native note or native card -> the card is deleted (removed from cards.json and all tabs); entity card -> unplaced from this tab only (the file is never deleted from the canvas); edge -> deleted; frame -> frame only (item 11). Multi-selection applies the rule per item as one undo step. Same via the toolbar trash and the inspector delete buttons.

17. Tab tree keyboard nesting. With a tab row focused/selected in the panel tree: Tab indents it one level (it becomes the last child of the row above it at the same level); Shift+Tab outdents it one level (placed right after its former parent). Indenting creates a portal card for the new child on the parent tab (placed at viewport center per item 15, nudged free); outdenting removes that portal card from the former parent (and only that one; other portals to the same tab elsewhere stay). Both are single undo steps and journaled. Same behaviour when a row is moved by drag in the tree. Tree rows are focusable (arrow keys move, Enter opens, F2 renames). Tree indent is Phase 1; the portal side of it lands with portals in Phase 2 (until then, Tab/Shift+Tab only reparent).
18. Empty-tab heading "An empty tab" still in Instrument Serif at ~24px: confirms item 5.

19. Cards can be dragged over the panel and inspector and render on top of them. Rules: (a) the rail, panel, inspector, top bar, toolbar and right pill are always stacked above the canvas layer, so nothing from the canvas ever paints over them; (b) the canvas viewport is the area between the panel and the inspector, and dragging a card past a canvas edge auto-pans the viewport (React Flow autoPanOnNodeDrag) rather than letting the card leave; (c) releasing a card while the pointer is over the panel's UNPLACED list unplaces it from this tab (the mirror of dragging in); releasing over any other chrome drops it back at its last valid canvas position. Layout writes only happen on a valid drop.

20. Top-bar tab chips reorder themselves on switch (active tab jumps to the front, MRU order). Rule: chip order is static and equals the tree order (depth-first, as in the panel); switching only moves the highlight. Order changes only when the user drags a chip or reorders in the tree, and both write the same `order` field. Child tabs appear as chips only while their ancestor is active (breadcrumb style) or not at all - keep the current behaviour but never MRU.

21. Rename in place: double-click on a tab chip in the top bar or on a tab row in the panel tree turns the label into an inline text field (text selected); Enter or blur commits, Esc cancels; empty name reverts. F2 does the same on the focused row. The inspector Title field stays as the third path; all three write the same title and are one undo step. Same gesture for frame titles on the canvas (already in 17.1) and, later, for tag names.
22. Breadcrumb ("Next canvas / Nummer 3") and the chip row collide when a child tab is active: the breadcrumb text runs under the first chip. Rule: the breadcrumb replaces the chip row's left part (root chips scroll right of it) or lives on its own line under the top bar; never overlapping. Chips show root tabs only, plus the active branch as the breadcrumb.

23. Deleting a tab is not undoable. Rule: tab delete (inspector "Delete tab", tree context menu, Delete key on a focused tree row) is undoable with Ctrl Z, restoring the tab file, its placements, frames, viewport, its position in the tree and any portals pointing at it, as one undo step. Entity files and edges are untouched by tab deletion anyway. Tabs with children: in-app dialog "Delete 'X' and its N child tabs?" (item 10 exception); leaf tabs delete immediately. Implementation: keep the deleted tab file in canvas/.trash/ (gitignored) until the undo stack drops it or the app closes; the journal records delete and restore.
   Observed after deleting the child "Sub-canvas" (under "Next canvas"): the chip disappears from the top bar, but the panel tree still shows it (row present, and the inspector still shows tab:nummer-3), and the breadcrumb still reads "Next canvas / Sub-canvas". The tab registry, tree, chips, breadcrumb, inspector and the active-tab route are out of sync: they must all derive from one store. After delete, the app navigates to the parent (or the landing if it was a root), the row and chip go, the inspector shows the new active tab. Whole tab delete/undo flow to be rebuilt against these rules and covered by tests: delete leaf, delete parent with children, undo each, redo each, delete the active tab, delete a non-active tab.

## Bugs fixed out of band (not spec changes)

B1. Marquee-selecting 2+ cards crashed with "Maximum update depth exceeded" (CanvasView.tsx, selection state mirrored back into React Flow). Fix prompt given 2026-09-12; verify Ctrl G and Align on marquee selections afterwards.
B2. Same crash, same location (CanvasView.tsx:704, Inner, `<ReactFlow<CanvasNode, TypedEdgeType>`), when confirming a relation in the edge type picker after dragging a connection (stmt:1 -> stmt:2). The type picker itself opens fine. Treated as the same root cause as B1 (app state written back into React Flow's nodes/edges props in an effect that re-fires on every change). Combined fix prompt given 2026-09-12.
B3. With an edge selected (stmt:2 -> stmt:3, clarifies): "Delete edge" in the inspector, the trash icon on the floating edge toolbar, and the Delete key do nothing; changing FROM/TO side in the inspector dropdowns does nothing; there is no way to drag an edge endpoint to another handle on the canvas. The edge type picker also stays open after confirm. Spec 8 requires: Delete removes the edge; fromSide/toSide editable from the inspector and by dragging an endpoint to another side handle (React Flow reconnect). Likely the same write-back problem as B1/B2: edge mutations never reach edges.json / the store, or the picker intercepts clicks.
