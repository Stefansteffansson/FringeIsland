**D4 — Sibling-pointer test reframed to operative-for-this-entity.** The tier-file-coverage test (does the tier file already enumerate the sibling) is necessary but not sufficient; the operative test (is the structural-relationship-to-sibling content load-bearing for working in this entity) is what justifies inclusion. ## Methodology observations — promotions, candidates, and inheritances

This section is structurally larger than Session 2's because Session 3 inherits two candidates from Session 2 (A and B), produces four new ones (C, D, E, F), and promotes one (F) to locked methodology this session.

### Promoted this session

**Methodology — Overlap-naming attaches to tier-file pointer in Where-to-go-next, mode-agnostic.** *(Previously tracked as Candidate F in earlier Session-3 commit messages.)* When tier-file content overlaps with this entity (tier file uses the entity as a concrete example, or entity content is an instance of a tier-level pattern), the overlap is named explicitly in the entity's tier-file pointer in Where-to-go-next so a future reader doesn't misread the pattern's origin or add it back for symmetry. Three instances grounded the structural validation: Privacy (substantive; non-restatement of tier file's RLS-vs-affordance gotcha example), Transactions (substantive; deliberate-restatement of tier file's "mishandled money" Purpose example), Observability (stub; non-restatement of tier file's canonical-example obligations drawn from Observability §6). Mode-agnostic by construction: the slot (tier-file pointer) exists in both substantive and stub modes; the pattern's mode-agnostic application follows from how the pattern is defined. Three within-session instances confirm the structural argument rather than provide the only evidence for it. Promoted to locked methodology; future entity files apply it.

### High-evidence candidates — ready for promotion on fourth-instance evidence

**Candidate D — Standalone anchoring over sibling contrast as cross-reference discipline.** When entity-file content would naturally invite contrast with a sibling, anchor via positive elaboration instead. Three within-session instances spanning distinct content types and structural locations: the Privacy/Transactions B/C cuts (in-file references to sibling vertical's analogous discipline cut from Rule 3 and Gotcha 3); Core's R1 "default answer is no" (doesn't reference Domain even though "Core change wanted, Domain Service needed" implies contrast); Domain's facet 3 (anchored via "owning its own data and contract surface" rather than via contrast with Core, with ADR-U023 carrying the canonical record of asymmetry). Underlying logic: coupling-reduction — entity-file content coupled to a sibling's specific phrasing rots when the sibling's phrasing changes. Standalone anchoring is one coupling-reduction technique; whether it's the canonical technique vs one of several available techniques requires more cross-context evidence to assert. Three within-session instances are suggestive; the structural validation is real but interpretive. **Second-instance test:** Session 4 or any future entity-file authoring session that produces a fourth instance — if standalone anchoring is the natural shape when sibling-contrast is available, the candidate generalises and earns promotion. If a future case emerges where standalone anchoring forces awkward shapes and sibling-contrast was the right call, the candidate falls away.
