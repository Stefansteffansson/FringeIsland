## Tensions and non-obvious insights

**The "stop and fix" discipline pays for itself in the same session it's applied.** The most concrete demonstration: the ADR-link verification step caught three filename errors in roughly thirty seconds. Without verification, the SPECIFICATION.md would have shipped with three broken links into a freshly-authored canonical document. A `doc-health-check` run would have caught them eventually, but the cost of "in committed history → noticed in next health-check → fixed in a follow-up commit" is much higher than "caught in pre-commit verification → fixed in same session." The same logic applied at a smaller scale to G-27 and G-28: writing the gaps down in the same session that surfaced them takes ~5 minutes; deferring to "future session" risks the findings evaporating. **The discipline isn't "fix everything inline"; it's "register or fix everything inline; never let a finding evaporate."** Worth noting because the temptation in a long session is to bank findings as "nice catches for next time" — and "next time" is where things drift.

**The L2 walk confirmed the partition skeleton, but the cleanest validation is what *didn't* happen.** Eight L2 sections, no force-fits, no obviously-missing concerns, no place where the template asked for content that the source material couldn't fill at the right level. The §L3 and §L4 placeholders sit cleanly without polluting §L2 work. The discipline of "L2 doesn't read existing feature specs" was easy to honour — the templates are designed for it. **The sharpest test was Section 4 Data ownership.** A naive reading would have looked for "tables Hub writes to" and either invented some or marked it incomplete. The honest answer is "none — Hub never accesses the database directly per ADR-U009," and that *is* the right L2-level claim about the Hub's data ownership. The template tolerated the inverted answer; the SPECIFICATION reads correctly with it. Pattern worth naming: **inverted answers (the entity's relationship to a section is "none, by architecture") are first-class outputs, not gaps.**

**The "load-bearing rule as anti-pattern catch" pattern recurred at the SPECIFICATION layer.** Prior bridges noted this pattern at template-design time (studio template's §5 Target Domain Service contract; platform-core template's §4 explicit "what this area does NOT depend on"; design-system template's §2 and §L3 explicit allowed/disallowed lists). Today the pattern showed up *inside* a SPECIFICATION: the §3 Auth & authorization commitment to "branch on permission, not role string" is not just guidance — it's a load-bearing rule lifted to spec-grade visibility so feature authors who skip the tier `CLAUDE.md` cannot silently violate it. **This is the third level the pattern has appeared at**: skill prose (root `CLAUDE.md`), template structure (Block A templates), and now spec content (Hub L2). Worth promoting to a documented design principle in `ecosystem-decomposition` if it appears at L3 or L4 too. Provisional name: *load-bearing-rule-as-anti-pattern-catch* (carried forward unchanged from prior bridges). Still don't promote yet — wait for L3 / L4 evidence.

**The citation-by-inference failure has a clean shape that's worth preserving for future-skill design.** The three ADR mismatches today all had the same shape: I knew what the ADR *was about* (the V4 anatomy lock; visitor anonymous sessions; the five cross-cutting verticals), and I inferred the filename from the *concept* rather than verifying against the listing. The fix discipline (G-28) is the right one, but the *failure shape* is more interesting: **memory stores concepts well and filenames poorly.** This is true of human memory and probably of mine. Skills that ask authors to cite filenames are asking memory to do something it's not good at; skills that ask authors to *verify* filenames against the disk are asking memory to do something it doesn't need to do. Worth keeping in mind when designing future skill rules — "verify against disk" is structurally easier than "remember correctly."

**Today's two new gaps were both findings that the discipline surfaced, not findings the system invented.** G-27 was visible from a 30-second read of `PRODUCTS_AND_PLATFORM.md` against the current ADR landscape. G-28 was visible from one session's three-citation failure pattern. Both were also visible in prior sessions (the strategy doc has been authoritative since the skill was written; the citation pattern has been latent since templates with ADR references existed) — they just weren't *named* until the inline-fix discipline forced the question "what should we do about this?" rather than allowing the answer "leave it for later." This is the strongest argument for the discipline: **the gaps were already there. The discipline is what makes them visible.**

**The progressive-disclosure README pattern survived its first non-cleanup test.** A.3-author and A.2-author each cleaned a tier README (`core/README.md`, `design-system/README.md`) when the corresponding template landed. Today wasn't a cleanup session, but the same shape applied: when SPECIFICATION.md landed, `hub/README.md`'s "to be written" line was updated in the same commit. **Three sessions in a row, same discipline, same outcome.** The pattern is now stable enough to name explicitly — *when a SPECIFICATION.md lands, the entity's README is updated in the same commit to reflect the file's existence and authorship state.* Smaller cousin of the README index discipline already named in `doc-health-check`. Worth raising at retro if it continues holding.
