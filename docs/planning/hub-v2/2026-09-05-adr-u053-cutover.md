**The sixth finding — a small-population race, found by the second full run (26 red, all one cascade):** from the bulk journey's force sign-out onward every operator request answered 401. The dev-server telemetry settled it: alone, the bulk actions requested 2 members; in the full run they requested **4** (reactivate: 4 requested, 2 succeeded — the two extras were already active). Four is the test project's whole population: A, B, the standing DeusEx member and **the operator**, whose session the force sign-out revoked. Mechanism: the spec's precondition waited only for A and B to be visible; on production's population the unfiltered first page never held them, so the wait was satisfied only by the applied search — by accident. On the test project the unfiltered page shows them at once, and the whole chain (two waits, "Select page", the action, the reason, Confirm) fits inside the list's 300 ms search debounce on a warm server, so "Select page" took the unfiltered page and the request body carried everyone. The ceremony *did* name all four; the spec never read it. The search request only precedes the POST in the log because the POST took longer to complete. The five-file re-run's "lost session" symptom (the earlier watch item) was this same cascade, not a cold-server guard path. **Fix (spec only; the surface is honest):** the precondition is now *exactly two rows* after the search — a state only the applied search can produce on any population — and `selectThePair` asserts "2 selected" before every page-scoped action, which is the spec's own promise ("force-logs-out FIXTURES only, never the session FIM") made executable. Class rule for the cascade: **a spec that relied on production's size for isolation is racy on the test project; assert the exact fixture count, never mere presence.**
