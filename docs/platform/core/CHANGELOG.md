# Changelog — Platform Core

Substrate-level changes to Platform Core (Infrastructure, Identity, Organisation, Governance). These are developer-facing platform changes, not end-user features; each entry links the feature spec with the full implementation notes.

## 2026-08-07 — Publication scope, the scoped offer, and diff-on-copy ([FEAT-PC028](./features/FEAT-PC028-role-template-publication-scoped-offer-and-diff-on-copy-contracts.md), Cycle RD-B) — gate closed + applied 2026-08-07

- **`role_template_publications`** (PC-3, migration `20260807090000`): publication reach as data (RD-8). A nullable `group_id` means platform-wide, so "all groups" is never a special code path. The nullable column forces a uniqueness question the constraint syntax does not answer for free — in a plain `UNIQUE`, **NULLs are distinct**, so a second platform-wide row would be permitted. Guarded by a **partial unique index**, the mechanism with three repo precedents, over `UNIQUE NULLS NOT DISTINCT`, which has none. RLS on; no write grant below `service_role` (ADR-U038 — the contracts are the only door).
- **`admin_publish_role_template` / `admin_unpublish_role_template`** (PC-4): idempotent (`already_published: true` rather than a unique violation, matching `admin_retire_role_template`'s shape), audit-logged on success and refusal, refusing a retired template, and refusing an **empty** group array `22023` rather than reading it as platform-wide. Publication rows **survive** retirement, so an unretire restores the prior reach instead of silently publishing to nobody.
- **`get_available_role_templates(p_group_id)`** (PC-3): scope- and retirement-filtered server-side, so every Surface inherits both by calling the contract. Carries adoption state (`adopted_group_role_id`, `adopted_version_number`, `current_version_number`) so a three-state render costs one read — both keys added by the decomposition payload walk, before either spec went `4-ready`.
- **`get_role_copy_diff` / `apply_role_template_update`** (PC-3): the diff is computed against the group role's **current** grant set, never version-vs-version. A version diff renders the *template's* changelog and hides the *Steward's* divergence, so a permission deliberately revoked would be silently re-granted — escalation by merge wearing a diff's clothes. Apply makes the grant set *equal* the template's, never a union, re-stamps provenance, and reuses PC025's `is_protected` for the lockout guard by **definer**.
- **Three `notification_kinds`** in a new `roles` category, `dispatch_segment` **NULL** (passive by construction, asserted rather than set). Separate from `platform` deliberately: a member mutes a category as a unit, and muting admin announcements must not silently mute "a role your group holds has changed".
- **`create_group_role` re-issued — the write-door fix.** RD-A filtered the picker read and left this branch validating **existence only**, so a retired clone stayed adoptable by id straight over PostgREST. Driven end-to-end before the migration was written (commit `ab2cc7b`), not inferred from the function body. The `manage_roles` check and `assert_group_writable` still fire **first**, unchanged.
- **`create_engagement_group` re-issued** with `retired_at IS NULL` on both instantiation branches (RDB-4). Defensive depth: the hole is unreachable today because only system templates are registered in `group_template_roles` and system templates cannot be retired. **RD-9 is recorded as ruling against a path that does not exist** — publications are `role_template ↔ group`, while that path reads `group_template_roles`, which no publication row touches.
- **`admin_retire_role_template` and `admin_set_role_template_default_version` re-issued** to emit their notices. Recipients resolve by **`manage_roles`**, not `assign_roles` — the permission that gates the act the notice is about. The two sets coincide today and diverge the moment a group defines a roles-only delegate.
- **`get_role_templates()` (zero-arg) DROPPED**, not shadowed. Scoping needs an argument; a signature change cannot be a COR-A re-issue (that discipline exists so create-or-replace preserves the ACL), and an overload would have served the unscoped catalogue to any caller that omitted it. Its single BFF wrapper moved in the same change.
- **A regression caught by the E2E fleet, worth recording.** The scoped read raises `42501` without `manage_roles`, where the dropped catalogue was open to any authenticated caller. Composed naively in the roles route's `Promise.all`, that refusal took the whole route to a 403 — so a *limited assigner* (holds `assign_roles`, not `manage_roles`) lost the entire roles panel. A refused offer now degrades to an empty list, which is the specified surface behaviour; the rule stays in the contract.

## 2026-08-06 — Role provenance, central retirement, group-side removal ([FEAT-PC027](./features/FEAT-PC027-role-provenance-retirement-and-group-side-removal-contracts.md), Cycle RD-A) — gate closed + applied 2026-08-06

- **The provenance stamp** (migration `20260806170000`): `group_roles.created_from_version_number`, a denormalised integer read from the live `role_templates.default_version_id → role_template_versions.version_number` — the version whose *materialisation* the copy doors actually consume. Not an FK: `role_template_versions.role_template_id` is `ON DELETE CASCADE`, so an FK-only stamp would evaporate — the exact dangle RD-4 exists to prevent. Landed at **all three doors** (`create_engagement_group`'s single insert serves doors 1 and 2; `create_group_role`'s template branch is door 3). The copied-date needed **no** column — `group_roles.created_at` was already set by every door.
- **The honest-unknown backfill (RD-10):** unambiguous grant-set match against `role_template_versions` or NULL, never a guess. Applied result: **1771 stamped, 1 left honestly unknown** (a `Member` instance in the FringeIsland Members system group whose grants had drifted from its template's only version), 4656 custom rows untouched.
- **Central retirement as pure offerability:** `role_templates.retired_at` + `retired_by`, with `admin_retire_role_template` / `admin_unretire_role_template` (PC-4, registered in the ownership manifest in the same migration). Retire writes two columns and one audit row — **no** `group_roles`, `group_role_permissions` or version row is touched anywhere (RD-2/RD-4), asserted directly by digest comparison rather than by absence of error. System templates refused; both verbs idempotent; refusals audited as refusals.
- **Both picker reads re-issued:** `get_role_templates` gains `retired_at IS NULL` (SECURITY INVOKER preserved — the body changed, not the enforcement point); `admin_get_role_templates` keeps retired rows and serves `retired_at` on every entry, so the admin plane shows the whole catalogue including what it has stopped offering.
- **`role_fabric_entry` widened** — this, not `get_group_roles`, is where each role entry is built, so the two new keys reach the fabric the panel already reads with no new round-trip.
- **Group-side removal:** `delete_group_role`'s template-derived refusal removed. The held-by-members `P0001` is inherited **unchanged** (Open Q3's never-cascade default), `assert_group_writable` still fires first, and PC025's existing `permissions.is_protected` is reused for a self-lockout guard — no second protected-permission concept.
- **Finding 3 corrected before build:** the dossier claimed the delete refusal was three layers deep and listed an RLS rule first. HYG-A had already dropped the `group_roles_delete` policy (`20260803190000:4533`) and revoked the DELETE grant (`:4545`); the comment cited as evidence is a **tombstone** the same migration left when it moved that rule into the contract. **This migration therefore carries no RLS delete change** — re-adding one would re-open the direct-PostgREST path HYG-A deliberately closed (ADR-U038). A guard cell asserts the policy set and the absent grant so a later "relax the RLS rule" reading fails loudly.
- **RD-5's guard corrected from "no holder" to "only definer":** the held-check fires first, so by the time the lockout is evaluated the role provably has zero holders and a holder-based test could never fire. Two constraints learned at build narrow it further: `prevent_last_leader_removal` means the Steward instance can never be made unheld, so the guard fires only where some *other* role is the last definer. Defensive depth, correctly placed, rarely reached.
- **Gap found and filed, not fixed:** `set_group_role_permission` carries **no** `is_protected` check on the revoke direction, so a group can be bricked by flipping a grant off rather than by deleting a role — the outcome RD-5 exists to prevent, through a neighbouring door RD-A did not close. [TASK-RDA-03](../../planning/backlog/tasks/TASK-RDA-03-set-group-role-permission-lacks-protected-guard.md), which leads with verifying the brick end-to-end rather than treating the reasoning as proven.

## 2026-06-27 — Mist ephemerality, transcendence, and the consent substrate ([FEAT-PC002](./features/FEAT-PC002-mist-transcendence-reaper-consent.md), IDN-2 — entry backfilled 2026-08-01)

- **`consent_records`** (`subject_user_id`, `subject_group_id`, `purpose` as open text, `policy_version`, `capture_context jsonb`, `captured_at`) with a **single** policy `consent_records_select_own` and the `enforce_consent_append_only()` trigger — no write policies at all; every write arrives through a `SECURITY DEFINER` path.
- **The ephemerality reaper** — `pc2_config` (key/value PC-2 config, RLS deny-by-default; `mist_inactivity_ttl` = 72 hours, seeded not hardcoded) + `reaper_runs` (the DB-side V4 sink, because pg_cron has no Hub to emit from) + `reap_expired_mists()` + **`pg_cron` enabled** and the `mist-reaper` job at `*/15 * * * *`. The race guard is inactivity plus `FOR UPDATE SKIP LOCKED`, not an in-flight marker column.
- **`_erase_mist(uuid)`** — the one erasure-cascade primitive shared by the reaper and by owner-invoked `explicit_erase_mist()` (authorizes by `auth.uid()` + `is_temporary`, `42501` otherwise). Its cascade **order** is load-bearing: journeys (FK RESTRICT) → `auth.users` (CASCADE drops the profile) **before** the proto group, which dodges the `personal_group_id` ON-DELETE-SET-NULL immutability trigger.
- **`finalise_transcendence(p_policy_version, p_capture_context)`** — one transaction: authorize, flip `is_temporary => false` **in place** (same row, same id), enrol the personal group in FringeIsland Members, write the transcendence consent record.

Anonymise-first is **structural, not procedural**: the consent FK `ON DELETE RESTRICT` blocks a raw hard-delete (`23503`), so the subject link must be NULLed first while `purpose` / `policy_version` / `captured_at` / `capture_context` are retained intact as proof. It refuses `is_temporary = true`, so the two erasure paths cannot reach the same row by construction.
