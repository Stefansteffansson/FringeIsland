### 1. Purpose

PC-4 Governance owns the answer to *who is authorized to act at the platform level, and how is system-wide state kept honest?* — the layer above PC-3's "who is this actor in the group system" answer. PC-4 turns platform-admin authority into concrete admin operations (decommission, hard-delete, force-logout, send-platform-notification), records durable audit trails of those operations, owns the moderation surface (member sanctions, content retirement, group closure at platform discretion), and enforces platform rules (terms of service, code of conduct, automated abuse handling). PC-4 is **domain-agnostic** in the Platform Core sense: admin authority, audit logging, moderation primitives, and platform-rule enforcement are not FringeIsland-specific concerns — every multi-user platform with admin-tier authority needs these. PC-4 does *not* own authentication or sessions (PC-2 Identity), groups / memberships / roles / permissions (PC-3 Organisation — though PC-4 consumes these), the RLS substrate or migration discipline itself (PC-1 Infrastructure), or any domain-scope content (Domain Services consume PC-4, never define it).

Per ADR-U028 (governance by scope, ratified 2026-06-10), governance splits by **scope**: community-scoped care (a Steward moderating their own group, a Guide facilitating their journey) stays **woven in-place** in the FIM experience via the PC-3 per-group role templates — no separate surface; the affordance appears where the care happens. Universe-scoped governance (economy, portfolio, legal, platform operations) happens on **the Console** — a distinct back-of-house surface ("the Console" is the working name; the fiction name is deferred). The Console is a surface, not a new permission system: one permission mechanism throughout (ADR-U006/U007). See the §2 enterprise-plane sub-section below.

#### Governance by scope and the enterprise-stewardship plane (ADR-U028; added 2026-06-10)

Per ADR-U028 and the roles core (`docs/ecosystem/universe/roles/README.md`, L2), the enterprise-stewardship plane has named human seats, all realized via the universal group pattern (groups + role permissions; no new permission mechanism):

- **Universeers** — care domains spanning the whole Universe: constituency, portfolio, community, economy, legal.
- **The FringeIsland Council** — major decisions concerning FringeIsland and its connection to partners.
- **DeusEx** — the **human root-admin group of the running platform** (ratified 2026-06-10): the people who administrate and maintain FringeIsland in the eyes of all users. Their permission set includes the authority of last resort (ADR-U019 — confirmed as the permission profile; the *role* is broader than break-glass). They act within the platform; they touch ecosystem development at releases and as a stakeholder, feeding observations of platform life back to the developers — DeusEx is the link between life inside FringeIsland and the development of the ecosystem. This formulation extends, and is consistent with, the Platform Admin Role concept row above (DeusEx system-group membership remains the schema realization).

Community-scoped care roles are the PC-3 per-group templates (Steward / Guide / Participant / Observer — Participant per the ratified 2026-06-10 rename of the group role "Member"); universe-scoped seats are the enterprise plane above. No other ad-hoc admin roles are introduced.

**Ferd routing (locked per ADR-U028), recorded where this spec covers the affected features:** content reporting/moderation surfaces **in-place** (the Moderation primitives capability, currently latent, lands as in-place community-care affordances, not Console panels); the **audit-log viewer** and **feature flags** route to **the Console** (universe scope); **self-service platform-exit stays in-experience** (a member leaving is not an admin act — this supersedes, at the spec level, the D-R3 "admin-assisted, NOT self-service" posture recorded at Step 2 C1-2; the current code path remains admin-assisted, and the code correction is deferred with the code correction target).

### 3. Contract surface — what this area exposes and to whom

Following PC-3's framing (PostgREST RPC as canonical realized HTTP API surface; custom Next.js routes as escape-hatch per three-justification design rule at PC-3 §7), PC-4's contract surface is:

#### Operations

Operations against PC-4 SQL primitives consume the Tier-1-only permission-gating pattern per ADR-U007 four-component scope (sentinel-UUID or literal-NULL `p_context_group_id`). HTTP-tier operations against PC-4's surface are realized today via two layers: (i) PostgREST RPC exposure of `public.admin_*` SECURITY DEFINER functions (default; see Public HTTP API surface sub-section above) — the canonical contract layer; (ii) custom Next.js routes (`app/api/admin/*`) for cross-table admin mutations + external API calls + multi-step transactions exceeding RLS-expressibility (RLS-escape-hatch; service-role escalated). PC-3 §7 carries the design rule that justifies a custom route over a PostgREST RPC; PC-4 inherits the rule directly without re-deriving.

#### Note on PC-4's "primitives, not endpoints" shape

PC-4, like PC-1, PC-2, and PC-3, is a special case relative to the template's default surface shape. Most of what it exposes is not a conventional REST API but a set of platform primitives — the platform-admin authority resolution function, the admin operation orchestration RPCs, the schema-level audit contract. Domain Services and Surfaces consume these through SQL or through the Supabase client libraries (PostgREST RPC for admin-RPC callers; admin-tooling routes for cross-table mutations). The PostgREST RPC HTTP API surface (above) wraps the SQL primitives at the HTTP layer; it does not replace them — same primitives, additional contract layer.

### 5. Storage & schema

**Sanction-state columns on `public.users` — PC-2 schema, PC-4 reference (analogous to PC-3 §5 cross-spec arrangement).** Per the §5 PC-2/PC-4 cross-spec disposition, the columns `is_active BOOLEAN` and `is_decommissioned BOOLEAN` remain on `public.users`. This places PC-4 references in a PC-2 table — a violation of the strict upward-only §4 chain on its face. PC-4's position is that this is an intentional override authorised by the platform-admin authority's structural 1:1 relationship to User account state: sanctions act *on* a User; the natural anchor for sanction state is the User row itself; placing the columns on a PC-4-owned table would require joining on every User-row read to evaluate suspension state, an unaffordable cost for a structurally 1:1 relationship. The alternative shapes (a `user_sanctions` table on the PC-4 side, with one row per User in active or sanctioned states) would relocate the coupling rather than eliminate it, at the cost of an extra index lookup on every authenticated request that needs to filter on sanction state (which is most of them). The override is currently §5-prose-anchored; if §8 Q5 disposition surfaces evidence that sanction-state semantics has grown beyond two booleans (e.g., `suspended_until TIMESTAMPTZ` for time-bound suspension, `decommission_reason TEXT` for audit-trail purposes), Step 3 may revisit whether the relationship is still 1:1 or has become 1:N (multiple sanction events per User over time), at which point a separate PC-4 table becomes more natural.

Pattern is load-bearing PC-4-internal design — preserves traceable actor attribution across hard-delete. **Audit-write surface — three coexisting patterns per Step 2 C2-5**: (a) SECURITY DEFINER direct-INSERT in admin RPC bodies (5 sites); (b) SECURITY DEFINER trigger-mediated with admin-gating (audit_admin_membership_change + audit_admin_message_send trigger functions); (c) anon-key-client direct INSERT via RLS-gated table at UI tier (7 sites). ### 6. Authentication & authorization

This section documents four partitions: (i) the PC-1 / PC-4 RLS-substrate partition; (ii) the PC-3 / PC-4 permission-resolution partition; (iii) the PC-1 / PC-4 audit-trigger partition (Finding #3 routing); (iv) the `is_platform_admin()` ownership partition (open at §8 Q3). #### PC-1 / PC-4 RLS-substrate partition

PC-1 owns the RLS substrate itself — the migration discipline that every new table carries RLS without exception, the SECURITY DEFINER pattern, the PG17 RLS complexity-ceiling discipline, the simple-bodied helper pattern (`is_platform_admin()` whose body is intentionally minimal so it survives PG17's RLS complexity ceiling). PC-4 owns the *content* of its RLS policies — what counts as a permitted SELECT on `public.admin_audit_log` (platform-admin only, gated via `is_platform_admin()`), what counts as a permitted INSERT (audit-write SECURITY DEFINER primitive only), what UPDATE / DELETE policies enforce the append-only invariant (prohibition). The platform-tier rule "new tables require RLS — without exception" is the consumption discipline.

#### PC-3 / PC-4 permission-resolution partition

The permission-resolution question resolves at this §6, not at either spec alone. ### 7. Stability posture

Per `docs/platform/core/CLAUDE.md` ("Platform Core changes are rare by design") and ADR-U023, PC-4 sits at the highest blast-radius layer in the ecosystem (with PC-1 / PC-2 / PC-3). Changes to admin-authority semantics, audit-write discipline, or moderation-state primitives propagate to every tier consuming Internal API. Specific cadences and triggers:

| Aspect | This area's posture |
|---|---|
| **Change cadence** | ADR-required for any change to admin-authority semantics (e.g., adding a non-DeusEx platform-admin role), audit-content schema (e.g., adding / removing columns on `public.admin_audit_log`), or sanction-state lifecycle. Wave-boundary for moderation primitive changes (if PC-4 owns moderation tables per §8 Q1). Per-cycle with review for new admin RPC additions or new admin permissions added to `public.permissions` registry (admin permissions are PC-3-schema rows; PC-4 governs which ones are granted to DeusEx). |
| **Triggers a change** | Legal / compliance finding (GDPR audit-log retention requirement; regulator audit obligation); security finding (admin-tier RLS gap discovered; supervised-bypass leak); new vertical obligation (audit field added for new transaction type per ADR-U002 Administration vertical); scale ceiling hit (audit-log row count making SELECT-via-`is_platform_admin()` slow without partitioning). |
| **Review escalation** | Stefan reviews; for changes touching admin-authority semantics or audit-content schema, the review also requires evidence that every consumer's RLS policies have been audited for compatibility (silent-miscompile failure mode per PG17 RLS complexity ceiling applies); for changes touching DeusEx role identity, a wave-boundary migration window is required because DeusEx-membership semantics propagate to every Domain Service that gates on admin authority. |
| **Default answer to "we want to change this"** | Per `platform/core/CLAUDE.md`: "model it in a Domain Service or via the Extension System first." For PC-4 specifically: admin authority is structured by **scope + the universal group pattern** (ADR-U028) — community-scoped roles are the PC-3 templates (Steward / Guide / Participant / Observer); universe-scoped seats are the enterprise plane (Universeers, the FringeIsland Council, DeusEx). No OTHER ad-hoc admin roles are introduced: a domain need for "a new kind of admin authority" maps to additional permission rows on `public.permissions` granted via the group pattern (in code today: granted to DeusEx, the canonical platform-admin role with stable identity per PC-3 Q10 grandfathering), not to a new ad-hoc admin role. A domain need for "domain-scope moderation" routes to that Domain Service's own moderation surface, not to PC-4 moderation primitives — PC-4 owns platform-tier sanctions, not domain-scope content moderation. |
| **Deprecation pathway** | For SQL primitives (which include the PostgREST RPC HTTP surface — function-signature changes propagate to the RPC interface): signature changes go through ADR + version-bump-equivalent (a new function name; the old function deprecated but still callable until all consumers migrate). Either (a) admin routes are exempt per implicit convention (admin tools migrate together with platform; no client coordination overhead) OR (b) version-prefix omission is technical-debt warranting future migration. Disposition deferred to PC-4 amendment-list candidate at Phase 2 close-out OR doc-health-check at next cycle. |

**Public HTTP API surface — three-justification design rule inheritance from PC-3 §7.** PostgREST RPC is the canonical PC-4 admin-RPC HTTP API surface today; see §3 sub-section "Public HTTP API surface (PostgREST RPC)" for the contract-category framing. Custom Next.js admin routes (`app/api/admin/*`) apply selectively per PC-3 §7 design rule, inherited at PC-4 without re-derivation: **(i) cross-table mutations** the route must execute as a single transaction with non-RLS-derivable authorization; **(ii) external API calls** that require service-role privileges (e.g., email-send for admin notifications); **(iii) multi-step transactions** composing more than one admin RPC primitive.
