## What makes this sub-tier different

Platform Domain is the **iteration zone** of the platform. ADR-U023 splits the platform into two stability zones, and Domain is the half that changes more often within stable contract boundaries. A Domain Service's blast radius is bounded — it's the consumers of that service's surface, not the platform-wide blast radius a Core change carries. Iteration here isn't a deployment-cadence preference; it's a structural posture about how Domain *evolves* — capabilities get added, internal implementations shift, contract surfaces grow incrementally — within boundaries that protect everything around the service from each iteration. Working at this sub-tier means treating the iteration posture as the default authoring stance: prefer additive change to contract changes, prefer in-service evolution to cross-service refactors, and treat the stable-contract-boundary obligation as the load-bearing constraint that makes iteration safe at all.

Domain's upward boundary is the **Platform API** — the contract Domain Services expose to Products, Studios, the Design System, and (in future waves) Extensions (ADR-U023's named boundary between Domain and surfaces). The Platform API is structurally different from Core's Internal API in the trust direction it carries: Platform API consumers are not all in-tree (Studios are, but Products are increasingly cross-implementation as Gimbal lands, and Extensions per ADR-U008 are a future-wave open category). Coordinated migration across consumers cannot be assumed — backward compatibility is the default obligation, deprecation cycles are real, and a v2 endpoint coexists with v1 until every consumer has migrated rather than as a brief transitional window. Authoring against the Platform API requires acknowledging that the consumer set is open in a way Core's Internal API consumer set isn't, and the versioning discipline (ADR-U015) carries different practical weight as a result.

Domain is composed of **seven services and the Extension System**: DS-1 World Model, DS-2 Narrative (renamed from "Narrative Engine" per the Engine-suffix decision, `../../architecture/decisions/PENDING.md`), DS-3 Journeys (renamed from "Experience Engine" at its descent, same PENDING.md entry), DS-4 Content, DS-5 Communication, DS-6 Discovery, DS-7 Intelligence, plus the Extension System whose contracts live at `../extensions/`. Each service is independently modular — owns its own data, exposes its own slice of the Platform API surface, and evolves on its own iteration rhythm within the sub-tier's iteration-zone posture. The seven services are not partitions of one zone the way Core's four areas are; they are independently-owned modules per ADR-U023, each developable in isolation as long as its contracts hold. This shapes content placement in the cascade: rules that apply to all seven services and the Extension System live at this sub-tier file; rules specific to one service (e.g., Intelligence's AI-derived data obligations under Privacy, Communication's realtime-channel constraints) live at that service's eventual entity-level CLAUDE.md when its L2 specification is authored. The Extension System's own architectural posture — Ferd-wave non-closure constraint per ADR-U008 and ADR-U018 — applies across all Domain Services, not to one.

## Rules that only apply at this sub-tier

- **Authoring discipline for proposing a new Domain Service or significant inter-service refactor: the bar is "this cannot be modelled within an existing service or as an Extension."** Unlike Core's "default answer is no," Domain's default is "yes, within a service" — but the service's identity is locked. Adding a service or moving capability across services changes the Platform API surface and the inter-service dependency graph; both are stability-affecting changes inside the iteration zone. The authoring discipline of meeting the bar is: before writing a feature spec that crosses service boundaries or proposes a new service, name explicitly which existing service was considered and why it was rejected. Rejection has to ground in capability-mismatch ("this concern doesn't fit any existing service's domain ownership") or in cross-cutting-shape ("this is genuinely orthogonal to all seven services' concerns and warrants a new one"), not in convenience or iteration speed.
- **Platform API stability discipline is stricter than the platform tier's generic versioning rule.** The platform tier file carries API versioning (ADR-U015) and contract-changes-trigger-ADRs generically. The sub-tier specific is: Platform API breaking changes require both a v-bump and a deprecation window with named migration support for every known consumer category (Hub, Gimbal once it lands, Studios, future Extensions). "Every consumer migrated" is not a moment that arrives by itself; it's an outcome the deprecation discipline produces. Authoring a Platform API change without a deprecation plan is a smell: the change hasn't met the discipline's bar even if the v-bump is correctly applied.
- **Ferd-wave non-closure of Extension System pathways is sub-tier authoring discipline, not just an ADR constraint.** ADR-U008 and ADR-U018 carry the binding constraints (no hardcoded step types, no hardcoded group types). The sub-tier rule is the authoring discipline of recognising closure: when a Domain feature spec introduces an enum, a sealed type set, a closed permission list, or a switch-on-type pattern, the question is "could this be data-driven instead?" — and "could not, because [specific architectural reason]" is the only acceptable rejection. "Could but it's faster as an enum" is closure; the iteration-speed argument doesn't override the Ferd-wave constraint. This rule lives at sub-tier rather than at tier because closure failures only arise within Domain Service authoring; Core doesn't author features that introduce extensible-concept enums in the same way.

## Gotchas

- **Don't reach across service boundaries by direct call when the Platform API doesn't already cover the path.** The path of least resistance when one Domain Service needs something another has is to import or call directly — both are in-tree, both compile, the test passes locally. The failure mode is structural: it bypasses the service-boundary discipline, creates an undeclared cross-service dependency that the Platform API surface doesn't reflect, and breaks the independent-modularity property that makes Domain's iteration-zone posture work. The recognition test is mechanical: if Service A reads Service B's data or invokes Service B's logic, the call goes through the Platform API (or through Internal API + Core if Core is the right shared substrate), even when both are in-tree. Direct cross-service calls look local but break system-wide.
- **Don't introduce extensibility-closing patterns in Ferd architecture even when the Extension System isn't being built.** The Extension System is future-wave per the `extensions/README.md` Ferd-wave constraint, but Ferd architecture has to leave it openable. The recognition failure: a Domain Service author hardcodes an enum (step types, group types, role types, content types) because it's faster, on the reasoning that "Extension System isn't built yet, we can refactor when it is." That reasoning misses the point of the constraint — refactoring closure-patterns out is harder than not introducing them in the first place, and every closure pattern is a Ferd-architecture commitment that Eid-or-later work has to undo. The discipline is to write data-driven from the start; the Extension System being deferred is a wave-scope fact, not an authoring license.
