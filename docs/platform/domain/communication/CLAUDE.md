## What makes this entity different

DS-5 owns the **conversational and social-fabric state** of the platform — DMs and conversations, group-scoped forums, activity feeds, notification routing and in-platform delivery, journey-scoped social surfaces, and the branch-gated cord-health glance — never the social graph itself (branches and the crown are DS-1 world-state; DS-5 surfaces conversation *along* branches), never another layer's notification obligation (every layer emits its own triggers — ADR-U002; DS-5 routes, products surface), never attachment substance (DS-4 assets referenced opaquely by ID, the n=4 opaque-reference pattern), and never the Whisp's dialogue (the split is decided: DS-1 world-presence / DS-7 being). **DS-5 is code-rich**: the four founding tables were born in the D15 monolithic rebuild (schema predates this partition, PW-1). Since A-COM Cycle C-A (2026-07-20, FEAT-PD008) the conversation model is a participants junction + open `conversation_kinds` registry (`dm`/`group` seeded), `direct_messages` is renamed `messages`, and the realized contract surface is the conversation/message + forum/attribution contracts (FEAT-PD008/PD009) — the only write doors; the legacy framework-mechanism surface (Realtime `postgres_changes` on the conversational tables) is retired per ADR-U039. Its canon authority is the cosmology core's village/branch/cord sections plus the roles core, not a per-entity sub-page.

## Rules that only apply at this entity

- **The nine service-level invariants in the spec's §7 are architecture, not features.** The U021 lock (attribution is display logic over current membership; stored data never mutated for anonymisation; posts never deleted for member exit); no rankings, no counts on any social surface (own branches legible, the wider crown ambient); village-anchored surfaces FIM-only intrinsically (PC-2 status, not a DS-5 fence); Mist-communication ephemerality (TTL + explicit-erase + atomic transcendence migration, ADR-U031); the routing law (layers emit, DS-5 routes, products surface); non-closure on all kind registries (conversation/feed-event/notification-event/channel kinds — TEXT-keyed, never enums; `notifications.type` already realizes this); the cord-health consent triple (glanceable not diagnostic, invited not imposed, self first — only along a grown branch, DS-1's gate); opaque DS-4 references only (never embed renderable substance); writes gate by scope (community-scoped moderation stays in-place with the Steward, never the Console). A feature spec or migration violating one fails review.
- **Every DS-5 actor column is a personal-group ID** (`recipient_group_id`, `author_group_id`, `sender_group_id`, `participant_1/2` → `groups(id)`) — P-O1's strongest realized site. Never introduce a `user_id`-shaped actor column here; the actor primitive is `get_current_personal_group_id()`.
- **Realtime is the ADR-U039 socket doctrine, never `postgres_changes`** — private broadcast channels carrying server-originated content-free hints; ping-then-fetch; verify-on-signal (RLS on `realtime.messages` gates topic receipt). `conversations`/`messages` left the `supabase_realtime` publication at C-A; don't re-register DS-5 tables in it (the pre-U039 "publication-registered by migration" rule is retired — spec §8 Q7 records the resolution; `notifications`' membership is A-NTF's disposition).
- **The attachment seam is resolved (2026-06-10) — don't re-derive it.** Attachments are DS-4 assets referenced opaquely by ID; DS-5 owns the attach/detach act as metadata (`content.md` §8 Q7 records the same resolution from the owned side).

## Gotchas

- **ADR-U021's display law is realized (A-COM Cycle C-B, FEAT-PD009) — attribution rides `ds5_resolve_author_display`, never data mutation.** The ladder: active member → display name; departed → `'Former member'` (the CB-9 string); erased author → `'Unknown'`. Route any new author-display need through that one resolver — never a second ladder. Note `author_group_id ON DELETE SET NULL` is the *platform-exit* erasure shape — a different lifecycle event from U021's member-leaves-group scenario; don't conflate them in cascade work.
- **Conversations are participants-grain with data-driven kinds; forums are flat** (the `conversation_participants` junction carries membership + per-participant read-state; `conversation_kinds` seeds `dm`/`group`, one-DM-per-pair schema-enforced; the `enforce_flat_threading` trigger; threads are top-level posts via `parent_post_id`, no thread table). New conversation kinds are a registry row, zero schema change (spec §8 Q8); deeper threading remains a deliberate schema act — don't assume it exists.
- **Migration names under-describe here** — `sprint3_smart_notifications.sql` carries the stewardship-nomination flow (~60% of its body). Classify migrations by content, never by filename (the #4 watch's first decisive firing happened at this entity).
- **Cross-tier writes into `notifications` are channel material, not a pattern to extend.** PC-3-tier triggers and PC-4 admin functions INSERT INTO `public.notifications` directly — recorded in the cross-tier-write channel anchored at DS-3. Don't add new direct cross-tier writes; route new emission through the contract when it exists.
- **Avatars in messaging/forum surfaces are PC-2/PC-3 substrate consumption** (settled at DS-4's descent, `content.md` §8 Q2) — not a DS-5 boundary question; don't re-litigate.
