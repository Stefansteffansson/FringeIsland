## What makes this entity different

Transactions is the only vertical whose obligations are shaped by a **named external vendor with concrete API surface and operational semantics**. ADR-U011 locks the platform to Stripe Connect specifically, not to "a payment provider" abstractly. Stripe-shaped concepts pervade the obligation inventory — payment-provider abstraction, webhook handling, idempotency keys, Connect accounts, Stripe Tax — and authoring the spec means making continuous decisions about which obligations are Stripe-specific (and will rot if the platform ever switches providers or Stripe deprecates an API) versus which are vendor-agnostic (and survive provider changes). Money operations have asymmetric cost-of-being-wrong on top of this: the platform can recover from a logging gap or a missed notification; it can't easily recover from a duplicate payout or a charge against the wrong account. The vendor-discipline matters more here than it would in a less irreversible domain.

The second authoring asymmetry is **multi-jurisdictional tax**. Tax obligations are jurisdictional, not vendor-shaped — VAT, US sales tax (state-by-state), withholding regimes, registration thresholds. These obligations would exist if the platform switched away from Stripe entirely, because they track regulatory environments rather than vendor APIs. Tax also carries asymmetric cost-of-being-wrong on its own axis: a misfiled tax return in one jurisdiction can compound into liabilities the platform isn't capitalised to absorb. Authoring tax obligations means treating jurisdiction as load-bearing scope, not as an implementation detail to be filled in later.

## Rules that only apply at this entity

- **Distinguish vendor-specific obligations from vendor-agnostic ones; bracket the Stripe-specific bullets explicitly.** Obligations that depend on Stripe-specific concepts (webhook event names, idempotency-key conventions, Connect account flows, Stripe Tax integration) belong in bullets that name Stripe in their text — not because the platform is wedded to Stripe forever, but because a future provider change needs a visible refactor surface. Obligations that are vendor-agnostic (the ledger writes on transaction success, the price-display flow before confirmation, the refund-policy disclosure) don't need bracketing — they survive any provider change. The discipline is to write each obligation at the right level of specificity, not to abstract Stripe-specific concerns into vendor-neutral language that obscures what's actually being committed to.
- **The ledger is the platform's source of truth for money state; Stripe is one source feeding it, not the truth itself.** Obligations are written against the ledger, not against Stripe. "Refund recorded in Stripe" and "refund recorded in the ledger" are different obligations with different reconciliation properties; the platform commits to the latter. This rule lives at this entity because the ledger-as-truth posture is Transactions-specific — none of the other verticals carry an equivalent named-truth-keeper for their cross-tier state. Authoring an obligation that treats Stripe state as authoritative inverts the platform's commitment.
- **Tax obligations cite jurisdiction explicitly; don't paraphrase regulatory regimes into "tax."** "EU VAT" is not the same obligation as "US sales tax" is not the same obligation as "withholding on cross-border creator payouts." Each tracks a different regulatory regime with different rules about thresholds, registration, filing, and remittance. When the spec writes a tax obligation, the jurisdiction is named — `[EU VAT]`, `[US sales tax]`, `[withholding: jurisdiction TBD]` — so a future author can check the platform's interpretation against the actual rule rather than a generic-tax abstraction.

## Gotchas

- **Don't write retry semantics for irreversible money operations as if they were rollbackable.** "On payment failure, retry" is fine for the platform's internal state. "On payout failure, retry" without idempotency keys and without distinguishing transient-network-error from already-paid-but-unconfirmed can double-pay a creator. The obligation-authoring failure mode is treating money operations with the same retry semantics as non-money operations — silently inheriting a retry posture that's safe for logs and notifications but unsafe for money. When an obligation involves a money operation, name the idempotency expectation and name what "retry" means for that specific operation; don't assume the surrounding retry conventions apply.
- **Don't conflate Stripe webhook receipt with ledger write.** Stripe webhooks can arrive out of order, can be replayed by Stripe's retry machinery, can be missed if the platform's webhook endpoint is briefly unreachable. An obligation that says "ledger updates on Stripe webhook receipt" treats the webhook as the truth and the ledger as a derived view; that inverts the rule above. The correct shape is "ledger updates on reconciled Stripe state, with webhook as one input to reconciliation" — webhook receipt triggers reconciliation, but reconciliation is what the ledger commits to. The authoring failure mode is using webhook-receipt language as a shorthand for "Stripe says it happened" without separating the event from the reconciliation that turns it into platform truth.
- **Don't promise tax compliance the platform can't deliver in unregistered jurisdictions.** Tax compliance requires registration in each jurisdiction where the platform has tax obligations. The platform is not registered everywhere a user might transact from. An obligation that reads "complies with the user's tax jurisdiction" — written without scope qualification — commits the platform to compliance the underlying capability doesn't deliver. The authoring failure mode is over-promising at the obligation level when the underlying capability is jurisdictionally bounded. Either qualify the scope explicitly (registered jurisdictions only; unregistered jurisdictions tracked as §5 open question) or don't write the obligation until the registration posture is locked.
