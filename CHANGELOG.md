### Fixed — Cycle DM-A: direct messages stop outliving the people in them (2026-08-12)
- **A departing member's direct-message words are now erased, not merely unattributed** ([TASK-DM-01](docs/planning/backlog/tasks/TASK-DM-01-direct-message-erasure-gap.md) / FEAT-PD018, migration `20260812120000`). Direct conversations are **not group-anchored** — for `kind='dm'`, `conversations.group_id IS NULL` — so the cascade that clears a group's conversations never fired for them. Participants cascaded away, `sender_group_id` SET NULL, and **the message bodies stayed**, reachable through no contract and visible to no instrument. Found when the dev-DB reset deleted every group and every account and left **557 threads and 1 123 messages** standing.
- **The ruling is a CONTENT-level tombstone** (Stefan, 2026-08-12): the erased member's bodies go (`content` NULL, `is_deleted` true); the thread shape and the survivor's own words stay. **Author-level was rejected because it was already the live behaviour** — the sender map has always resolved a departed author to *Former member* — so choosing it would have been a no-op leaving the Article 17 exposure intact. And anonymising a name in a **two-party** thread obscures nothing: the survivor knows exactly who they were talking to.
- **The forum precedent deliberately does not decide this by analogy.** [ADR-U021](docs/architecture/decisions/ADR-U021-forum-anonymisation-soft-flag.md) keeps forum posts because a thread is communal and other participants have a legitimate interest in it staying intact; a private exchange of two has no such argument. Forum disposition is untouched.
- **Cascade specification (ADR-U016), because the five paths are not all erasures:** self-delete and hard-delete tombstone; **admin exit is a removal, not an erasure**, and is unchanged; decommission is a status change; and the **Mist leg is empty by construction** — `get_or_create_dm_conversation` refuses a temporary actor *and* a temporary recipient, so no Mist can be party to a DM. The residue class is closed structurally too: a DM thread left with no participant but the departing member is deleted outright.
- **`admin_hard_delete_user` documented a cascade that does not happen** — its comment claimed deleting the personal group cascaded conversations. Corrected in place, naming the mechanism and the consequence.
- **Caught at the gate review:** the migration changed shipped semantics without the **sibling-assertion sweep** the house rule requires — the fourth time that class has bitten. `PC017 S5b` was invalidated in three places, the sharpest being an assertion that the survivor could still read the departed member's words. **That assertion was the exposure itself.** All three adapted; the sweep is now named in the migration header.
- Verified at the gate: PD018 suite **9/9**, platform conformance **30/30**, full integration **1181/1181 across 84 suites**, applied ACLs read directly (the DS-5 fact handler sealed from client roles, nothing `anon`-reachable).

### Added — Phase 4 W7: sealed conversation threads become visible to the admin plane, bounded (2026-08-11)
- **A closed group's sealed threads can now be read by the admin plane, and only there** ([TASK-SEAL-01](docs/planning/backlog/tasks/TASK-SEAL-01-sealed-thread-admin-sight.md), migration `20260811220000`, realizing AB-6 **ruling B1**). Sealed threads (preserve-and-seal, FEAT-PD012) were invisible to *everyone*, including the admins investigating the conduct that put them there — G-4 had already ruled that admin sight of a group in trouble includes its conversations *because bullying evidence lives in messages*, and a sealed thread is exactly where that evidence lands when the author departs.
- **The ruling's own scope word was wrong, and the build stopped to say so.** B1 said "suspended-scope only". The Definition-of-Ready contract walk found that scope **unmatchable**: `sealed_at` has exactly one writer in the schema (`ds5_lifecycle_group_closed`), and all five of its callers seal *while setting the group to `closed`* — in `admin_remove_member_from_group` the seal fires one line after `UPDATE groups SET status='closed'`. Statuses are mutually exclusive, so the contract as ruled **could never have returned a row**, and with zero sealed rows on dev a green suite would have proved nothing. **Re-scoped to `closed` on Stefan's ruling**, then verified *exhaustive*: none of the five paths hard-deletes the group, so `closed` is where every seal lands.
- **The premise underneath B1 was verified against the substrate, not the spec text:** `messages.sender_group_id` is `ON DELETE SET NULL`, so a departed member's messages **survive with authorship tombstoned**, while conversations cascade only from the group — which is closed, never deleted. The evidence really does outlive the author.
- **Shape follows the ADR-U047 Amendment 3 declared-composition class** rather than the shortcut Audit IV caught: a **sealed** DS-5 body (`ds5_admin_group_conversations`, EXECUTE revoked from client roles — verified `{postgres, service_role}` on the applied object) owns the read, and a PC-4 wrapper (`admin_get_group_conversations`) owns the admin wall and the closed-scope rule. Both registered in `supabase/ownership.manifest.json` with a `declaredCompositions` entry, without which the invocation-axis gate fails.
- **The other three bounds are intact:** group-kind conversations only (direct conversations never returned), the sealed state returned **explicitly** (`is_sealed` + `sealed_at`) so no surface can render a sealed thread as live, and `get_group_conversations`' own `sealed_at IS NULL` member-plane law **untouched** — pinned by a cell that must pass on both sides of the apply.
- Red-then-green (**6 red → 8/8**); platform conformance **30/30**; communication slice **107/107**. **The Hub surface that renders the sealed label is a paired follow-on and is not built.**

### Fixed — Phase 4 W8: a group can no longer be bricked from inside through the grant-flip door (2026-08-11)
- **`set_group_role_permission` now refuses a revoke that would leave the group with no definer of a protected permission** (migration `20260811210000`, [TASK-RDA-03](docs/planning/backlog/tasks/TASK-RDA-03-set-group-role-permission-lacks-protected-guard.md)). RD-A bound PC025's `is_protected` guard to the **delete** door (`delete_group_role`) and left the neighbouring one open: revoking `manage_roles` from the group's only role granting it left **nobody able to grant it back** — `set_group_role_permission` requires `manage_roles`, and `create_group_role`'s anti-escalation refuses to grant a permission the author does not hold. **The group was bricked from inside with no row deleted**, the exact outcome RD-5 exists to prevent.
- **The brick was confirmed end-to-end before the fix was designed**, as the task demanded rather than assumed: the red run's revoke returned `error === null` and drove `manage_roles` definers **1 → 0**. Red-then-green on one suite (2 red → **10/10**).
- **No repair pass was needed, and the survey that says so is worth reading twice.** 3 941 groups hold no definer for a protected permission — but **3 938 are personal groups, which are designed to carry none** (the zero-permission "Myself" role), 3 are system groups, and the one engagement group is a suspended dev fixture with no roles at all. Nothing reached this state through the door being closed.
- **The two doors now speak with one voice** — the refusal mirrors the delete door's wording and `P0001` verbatim. The delete door's own message was deliberately **not** touched: three live assertions bind it and the Hub renders it to Stewards.
- Verified at the gate: groups slice **404/404**, platform conformance family **30/30**, and the **applied** function's ACL read directly (`{postgres, authenticated, service_role}` — no PUBLIC, no `anon`), per the TASK-SEC-01 discipline.

### Fixed — TASK-E2E-04: the anonymous janitor was unbounded *and* blind (applied 2026-08-09)
- **The E2E teardown that swept anonymous users cost the whole database, inside a 30-second budget.** `cleanupAnonymousUsers` ran in a per-spec `afterAll` in the three Mist specs and was O(every anonymous user it could see) — and N *grows during a fleet*, because the fleet is what mints Mists. So teardown got slower the longer the fleet ran and failed only in a fleet, with a different victim each time. That is the whole recorded profile of this task, and it explains it without appealing to notification volume at all.
- **The same line was also hiding the opposite failure: the sweep could not see most of what it was meant to delete.** `listUsers({ perPage: 200 })` pages over *all* users and filters `is_anonymous` client-side. Measured before the fix: **2 978 auth users, 43 of them anonymous, and zero of those 43 inside the newest 200.** A running fleet's fresh Mists dominate page 1 and get swept; any Mist that falls off it becomes invisible to every later sweep, permanently. The oldest survivor dated **2026-06-27** — six weeks of residue behind a janitor that reported success every run.
- **One mechanism fixes both.** The batch is now resolved by SQL against `auth.users` — exact, one round-trip regardless of N, with the personal group carried on the row — and each spec bounds its sweep with a creation watermark read from the **database clock**, not the local one, so the two clocks cannot silently widen or narrow the bound. The unbounded sweep still exists and is still needed for residue, but is paid **once in global teardown**, where there is no 30-second budget. A malformed watermark throws rather than quietly degrading back into a full sweep.
- **Verified against the substrate rather than trusted:** anonymous users **43 → 0**, `auth.users` **2 978 → 2 935** (−43, exactly the sweep), and orphaned personal groups **954 → 954** — not one of those deletions orphaned a group, so TASK-INT-03's property held through the change.
- **Closure states the mechanism removed, not a count of green fleets** (the `TASK-E2E-01` discipline). The integration-tier half of this task — W-7's PAIR-shaped emission cells — is explicitly **not** closed by this: that tier never called the janitor, so this cannot be its mechanism.

### Added — RD-B walk fixes W-6 and W-9 (applied 2026-08-09)
- **The publish ceremony now states its blast radius before the click.** RD-B's whole discipline is *consequence before the click*, and the Steward's diff ceremony honoured it — naming the holder count and saying what happens to those people. The admin's publish ceremony said nothing, though its reach is two orders of magnitude larger (measured: 427 notices to 223 recipients across 425 groups) and **cannot be undone** — unpublish withdraws the *offer*, while the notices correctly stand, because they recorded something that was true. **We had held the smaller act to the higher standard.** Both ceremonies now read *"This will notify N stewards across M groups. Those notices cannot be withdrawn."*, from a new admin-gated read (`admin_preview_publication_reach`).
- **A preview that can drift from the act it previews is worse than no preview** — it states a confident number that is wrong. So the mirror is tested, not asserted in a comment: cell **W6c previews, publishes, then checks the preview equalled the rows actually created**. Editing one predicate without the other fails loudly. The count also degrades safely — a preview that cannot be read renders nothing and never blocks the publish.
- **A guaranteed refusal is no longer offered as a button (W-9).** Opening Delete on a held role used to warn that it would fail, take the click, and return the same sentence as an error — while `holder_count` was on screen the whole time, so the surface *knew*. Confirm is now disabled with the obstacle still stated; Cancel stays live. This is RD-A's behaviour, fixed under RD-A's story: RD-B only made it visible by putting a careful ceremony beside a careless one. It applies a ruling made once already, at the ADM-E walk (WA-1).

### Fixed — RD-B live walk (FEAT-H044 + FEAT-PC028 STORY-9), applied 2026-08-08
- **Two acceptance criteria had shipped `6-done` unbuilt, and the live walk found both in its first two clicks.** *Publish to named groups* (STORY-3) existed in the contract, the route and the lib — and had no UI, so the targeted publish that is RD-B's entire point was unreachable from the admin plane. *Each notice names its own group* (STORY-4) was not true of any of the three kinds: all said *"your group"*, so a Steward of five groups received five identical notices about five different groups. Both features are back at `5-in-cycle`.
- **The root cause is one mistake made twice: a fixture that invents a payload the substrate never produces.** W-5's unit cell asserted that named reach *renders* from a hand-authored `publications` payload — a state no door could create. W-8's asserted that two notice bodies naming different groups render distinctly — bodies the server never wrote. Both green, both meaningless, both passing at `6-done`. The payload walk traces **keys** and never asks what the **value** reads like; the N-E copy-check rider was meant to cover exactly this, but as practised it verified the strings the *component* renders in its own test rather than the strings the *server* authors.
- **Two rules now encoded in the suite.** When copy is server-authored, the copy check reads **the migration's literal**, never the component's fixture — a component test can prove the surface renders what it is given, never that the server gives it that. And when a feature adds a **write door**, at least one test must reach the state **through that door**: a fixture may set up everything the door is not responsible for, never the thing it produces. The RD-B E2E now signs an admin in and publishes through the picker instead of inserting the row — which is also what finally verifies the scoping claim (a group that was not named is not offered the template).

### Changed
- **"Sign out" is now local to the browser, not global across every device (FEAT-H012 — Stefan's ruling, 2026-07-27)** (2026-07-27) — **A decision, not a defect.** `supabase.auth.signOut()` defaults to `scope: 'global'`, so signing out on a laptop silently ended the member's phone and tablet too. That is the opposite of the near-universal convention: Google, Microsoft, Facebook, Apple, GitHub and Slack all treat "Sign out" as **device-local** and put *"sign out everywhere"* behind a separate, explicitly named control beside a device list. The reasoning is intent and cost — signing out is routine (a shared machine, the end of a day) and cheap to undo, whereas ending *every* session is a **security response**, a different mental mode, and costs N re-authentications. Surfaced by the W-05 sibling sweep, raised rather than changed (it alters a deliberate user action), and ruled the same day. `AuthContext.signOut()` and the Mist-erasure session drop both now pass `{ scope: 'local' }`, making **all five** sign-out call sites local and consistent: the session guard (W-05), `farewell`, the `/sessions` current-device revoke, the Mist farewell, and the account menu. Red-first: 2 unit cases demonstrated red (`Expected {"scope":"local"} / Received undefined`) → green; Hub unit 994 → **996/996**; profile + sessions E2E **7/7**; `next build` clean, eslint 0. **A prior note is corrected:** FEAT-H012 claimed `profile.spec` STORY-4 *depended* on the global scope — it does not; STORY-4 asserts only local effects. The real relationship was the reverse (global sign-out **server-revoked the shared storageState session**, which is why `sessions.spec` uses fresh logins), so this change *removes* a suite hazard. **Not included:** *"Sign out everywhere"* on `/sessions` is a new capability needing a platform bulk-revoke contract (today only `DELETE /api/sessions/[id]` exists) — a paired spec, deliberately not slipped in here.

Each migration must therefore revoke PUBLIC explicitly. A-NTF cycles N-A, N-B and N-C all wrote `REVOKE … FROM PUBLIC, anon`; **N-D wrote `FROM anon` alone on all seven of its contracts**, which is a no-op against a privilege held via PUBLIC.
